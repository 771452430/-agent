# 巡检 Agent 机制与功能说明

## 一句话介绍

`巡检 Agent` 是一个面向自动化巡检场景的智能协同能力。

它的核心目标不是“聊天问答”，而是把原本依赖人工盯盘、人工分派、人工通知、人工留痕的巡检工作，整理成一条可自动运行、可追踪、可沉淀的闭环流程。

---

## 功能定位

巡检 Agent 面向的是“问题池巡检”和“问题转派”这类自动化场景，适合放在 Jira、工单系统、问题面板等统一列表入口上使用。

它关注的是：

- 自动抓取问题列表
- 自动识别待处理项
- 自动匹配负责人
- 自动调用转派动作
- 自动发送通知
- 自动记录每次执行结果

因此，它和交互式聊天 Agent 是两类不同能力：

- 聊天 Agent 解决“人来提问、系统来回答”
- 巡检 Agent 解决“系统按规则主动巡检、主动流转”

---

## 解决的问题

在传统巡检方式下，通常存在几个共性问题：

### 1. 人工巡检效率低，且容易遗漏

- 需要人工定时打开面板查看
- 问题数量一多，容易漏看、晚看
- 高峰时段会明显增加人力负担

### 2. 问题分派依赖经验，不够稳定

- 谁来处理，往往依赖个人经验判断
- 新同学不熟规则，容易分错
- 老同学容易被频繁打断

### 3. 流程不透明，结果不易复盘

- 问题是否已处理，缺少统一留痕
- 分配是否成功，不容易回看
- 哪类问题最多、哪类问题最容易卡住，缺少可追踪记录

巡检 Agent 的价值，就是把这类“重复、分散、易遗漏”的工作统一收口，减少人工盯盘成本，提升问题流转效率。

---

## 机制说明

当前巡检 Agent 已经形成一条相对完整的执行闭环。

系统服务启动后，会自动带起巡检调度；同时，也支持人工在页面上手动立即触发。

整体链路可以概括为：

```mermaid
flowchart LR
    A["定时轮巡 / 手动触发"] --> B["拉取问题列表接口"]
    B --> C["解析问题列表"]
    C --> D["按需拉取详情"]
    D --> E["规则匹配负责人"]
    E --> F["模型兜底判断"]
    F --> G["调用转派接口"]
    G --> H["发送通知邮件"]
    H --> I["记录运行结果"]
```

### 当前 Jira 场景的真实处理方式

在当前落地场景中，巡检 Agent 不是只看一个接口，而是分两步完成问题识别：

1. 先请求 Jira 列表接口 `issueTable`
2. 再根据列表中的 issue，逐条请求 `AjaxIssueAction` 详情接口
3. 把列表数据和详情数据组装后，再进入负责人匹配和转出流程

这样做的原因是，很多真正用于判断和分派的信息并不完全在列表接口里，而是在详情接口里。

### 两种运行方式

当前支持两种运行方式：

- 定时自动运行
  适合日常持续巡检，系统按配置的轮巡间隔自动执行
- 手动立即运行 / 当前列表分配
  适合人工检查当前问题池、验证规则是否生效，或对当前列表做一次集中转派

## 核心能力

当前巡检 Agent 已经支持以下关键能力：

### 1. 灵活接入外部问题源

- 支持自定义请求方式
- 支持自定义请求头
- 支持自定义请求体
- 能适配不同来源的问题列表接口

### 2. 支持详情补全

- 不只抓取列表
- 支持在列表识别后继续拉取详情接口
- 适合需要通过详情字段完成判断和分派的场景

### 3. 支持规则优先分派

- 可按服务、模块、关键词、客户问题类型、负责人编码等维度配置规则
- 能让问题优先按照明确规则进入对应负责人

### 4. 支持 `fixed_match` 固定匹配模式

- 适合规则比较明确、希望直接按规则落人的场景
- 在该模式下，系统可按当前列表全量遍历处理，而不是只看新增问题

### 5. 支持模型兜底

- 对规则未命中的问题，可由模型给出兜底建议
- 规则优先，模型补充，降低纯人工判断成本

### 6. 支持自动转派

- 支持调用外部分配接口
- 匹配到负责人后，可直接进入实际转派动作

### 7. 支持通知与留痕

- 支持发送邮件通知
- 支持保存每次运行记录
- 支持回看抓取数量、分派结果和失败原因

### 8. 支持失败保护

- 连续失败达到阈值后，可自动停用对应巡检 Agent
- 避免异常任务长期无感运行
- 便于管理侧及时发现问题

---

## 当前重点规则与落地方式

当前规则配置支持多种维度组合，包括：

- 服务
- 模块
- 关键词
- 客户问题类型
- 负责人编码

其中，已经确认的一个典型规则示例如下：

- 当客户问题类型命中 `应用操作`、`需求问题`、`实施问题`
- 系统将问题分配给 `qiangxiao`

### `fixed_match` 的当前策略

当前 `fixed_match` 模式采用的是“全量处理”策略，而不是“只看新增”策略：

- 不只判断是否为新增 bug
- 每次直接全量拉取当前列表
- 对列表中的问题逐条拉取详情
- 详情补全后按规则进行匹配
- 匹配后直接执行转出

这类模式适合规则相对明确、希望快速完成当前问题池流转的场景。

## 运行结果与管理价值

从管理角度看，巡检 Agent 的价值主要体现在四个方面：

### 1. 降低人工巡检成本

- 减少人工反复打开面板检查
- 降低依赖专人盯盘的压力
- 让团队把时间更多放在真正需要分析和解决的问题上

### 2. 提高问题分派一致性

- 用明确规则代替临时判断
- 降低不同人处理同类问题时的偏差
- 让问题流转更加稳定

### 3. 缩短问题响应时间

- 系统自动发现问题
- 自动匹配负责人
- 自动推动转派和通知
- 能更快把问题送到该处理的人手里

### 4. 形成可追踪的分派记录

每次运行后，系统都可以输出并沉淀以下结果：

- 当前抓取数
- 解析后的问题数量
- 匹配与分配结果
- 邮件通知结果
- 失败原因
- 停用状态与连续失败情况

这意味着管理侧不只是“知道系统跑过”，而是能看到它实际处理了什么、效果如何、问题出在哪里。

## 当前边界与注意事项

巡检 Agent 已经具备较完整的能力，但当前落地仍然有一些现实边界需要明确。

### 1. 网络访问边界

- 当前 Jira 巡检接口依赖内网访问
- 如果部署环境无法访问内网 Jira，即使配置正确也无法完成抓取和转派
- 因此，公网环境不能直接等同于内网可用环境

### 2. 对外部接口有依赖

要让巡检 Agent 正常工作，需要保证以下基础条件成立：

- 外部列表接口可用
- 详情接口可用
- 外部分配接口可用
- 邮件配置有效

如果其中任一环节不可用，整条链路的效果都会受到影响。

### 3. 规则优先，模型只做兜底

当前设计原则是：

- 规则命中优先于模型判断
- 模型只做兜底，不作为唯一依据

这样做的目的，是优先保证分派的稳定性、可解释性和可控性。

## 后续扩展方向

在现有基础上，巡检 Agent 后续还有比较明确的扩展空间。

### 1. 支持更多问题源系统

- 不局限于 Jira
- 可扩展到更多工单池、问题池、项目面板场景

### 2. 支持更丰富的负责人规则

- 在现有规则基础上，继续增加更细颗粒度的分派维度
- 进一步提升自动分派准确率

### 3. 支持更完整的统计与管理报表

- 形成巡检量、转派量、失败量、分派命中率等统计结果
- 为管理决策提供更直接的数据抓手

### 4. 支持更多通知与协同方式

- 在邮件之外，进一步与飞书、企业通知等渠道联动
- 提升流转效率和触达效率

---

## 总结

巡检 Agent 的核心意义，不只是“做了一个自动抓接口的功能”，而是把问题巡检、问题分派、通知留痕这类重复性工作，逐步沉淀成一套可持续运行的标准化机制。

它适合承担的问题，是那些“数量多、节奏快、规则相对明确、人工盯盘成本高”的日常巡检工作。

从当前进展看，这项能力已经具备真实落地基础；后续如果持续补充规则、打通更多系统和通知渠道，它可以进一步演进成更成熟的自动化协同能力。
